# Phone Preview — Design

> Status: **Draft for review** · Date: 2026-10-16
> Follows the walking skeleton (`2026-10-12-walking-skeleton-design.md`). Requirements: `docs/SPEC.md`. Architecture: `ARCHITECTURE.md`, `docs/adr/` (ADR-0007 web first, ADR-0008 self-hosted).

## 1. Purpose

Make the web app usable as a home-screen app on the owner's iPhone, including opening with no connection, so the offline-first experience can be tried on a real device before more features are built.

**Who:** the owner only, testing on their own iPhone over the home network or VPN, against the stack on their PC (`https://<LAN_HTTPS_HOST>:8443`). Sign-in codes are read from Mailpit; real email delivery is out of scope.

**Covers:** FR-1 (staying signed in), FR-28 and NFR-4 (offline, now including cold start).

### Success criteria

1. Add to Home Screen gives an app with a proper name and icon that opens full screen, without Safari's address bar.
2. In airplane mode, launching it from the home screen shows the household's recipes and lets the owner add one; the recipe syncs once back online.
3. After a rebuild on the PC, the phone picks up the new version without the app being removed and re-added.
4. Local data and sign-in survive closing the app, restarting the phone, and days of not opening it.

### Out of scope

Real email delivery, native builds, production hosting, migration of local data between storage modes, push notifications, and any change to sync rules or the server API.

## 2. Decisions made during design

| Decision | Choice | Why |
|---|---|---|
| Offline app shell | A service worker generated by Workbox (`workbox-cli`) at build time | Workbox owns precache versioning, cleanup and updates, which is where hand-written service workers usually go wrong. It is build-time only; the app gains no runtime dependency. |
| Update behaviour | Install in the background; a banner offers "Reload" | An automatic reload could discard a half-typed recipe title. Saved recipes are in the local database either way. |
| Local storage mode | `OPFSCoopSyncVFS` on every browser | PowerSync recommends it for Safari/iOS; the default IndexedDB mode lacks multi-tab support there. Using it everywhere means the Chromium e2e suite tests what the phone runs. |
| Offline sign-in | A network failure while renewing the token keeps the saved session | Today it signs the user out and wipes unsynced data (see §5). |
| When to wipe local data | Explicit sign-out, or a different user signing in | Losing the session involuntarily must never lose unsynced recipes. |
| Icons | Generated once from `assets/icon.png` with Python PIL and committed | Placeholder quality is acceptable; no image tool joins the build. |

### Known consequences

- Switching storage mode starts each browser with an empty local database that re-downloads from the server. Anything unsynced in the old IndexedDB storage is stranded, so the phone must show "0 unsynced" before it loads the new version. The old IndexedDB database is left in place.
- OPFS has known issues in Safari private browsing. Private browsing is not supported; the app shows a message instead of a blank screen when the database cannot open.
- While offline with an expired token, the UI shows the last known household role. A write made after a demotion to viewer is rejected when it uploads, as today.
- The home-screen app has storage separate from Safari's, so the owner signs in once more inside it.

## 3. Pieces and build

### Installable app

- `apps/mobile/public/manifest.webmanifest`: `name` "Recipes", `short_name` "Recipes", `display` `standalone`, `start_url` and `scope` `/`, `theme_color` and `background_color`, icons at 192 and 512 px plus a 512 px `maskable` icon.
- `apps/mobile/public/index.html`: Expo's HTML template for single-output web builds. It keeps Expo's root element and adds `<link rel="manifest">`, `<link rel="apple-touch-icon">` (iOS takes the home-screen icon from this, not the manifest), `<meta name="theme-color">`, and `viewport-fit=cover`.
- Icons in `apps/mobile/public/icons/`: `icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `apple-touch-icon.png` (180 px).

### Service worker

- `build:web` becomes `copy-assets`, then `expo export --platform web`, then `workbox generateSW workbox.config.cjs`, which writes `dist/sw.js` and its runtime file.
- `apps/mobile/workbox.config.cjs`:
  - `globDirectory: 'dist'`, `globPatterns: ['**/*']`, excluding `sw.js` and Workbox's own files.
  - `maximumFileSizeToCacheInBytes` 5 MB. PowerSync's WebAssembly builds are up to 2.4 MB, and all four are precached (about 12 MB in total) rather than guessing which one a browser loads.
  - `navigateFallback: '/index.html'`, with `navigateFallbackDenylist` covering `/auth`, `/api`, `/sync`, `/email-templates`, `/local-ca.crt`.
  - `clientsClaim: true`, `skipWaiting: false`, `cleanupOutdatedCaches: true`. No `runtimeCaching`: only precached files are served by the worker.
- New development dependency: `workbox-cli`, in `apps/mobile`. The proxy image build runs it, since that is where `build:web` runs.

### Registration and updates (`apps/mobile/src/pwa/`)

- `registerServiceWorker.ts`: in the production web build only (`process.env.NODE_ENV === 'production'` and `'serviceWorker' in navigator`), registers `/sw.js` once from `app/_layout.tsx`. It also calls `registration.update()` when the page becomes visible again, because iOS home-screen apps often resume rather than restart. It uses the browser API directly (about 40 lines), not `workbox-window`.
- `useUpdateReady.ts`: reports when a new worker is installed and waiting. `applyUpdate()` posts `{ type: 'SKIP_WAITING' }` (Workbox's generated worker listens for it) and reloads on `controllerchange`.
- `UpdateBanner.tsx`: "A new version is ready. Reload." Shown on every screen from `_layout.tsx`.

### Build label and storage status

- The proxy Dockerfile sets `EXPO_PUBLIC_BUILD_TIME` (UTC, minute precision) before `build:web`. The image stays free of host names and secrets.
- A footer line on the recipe list and sign-in screens: "Build 2026-10-17 14:05 · Storage: persistent" (or "best effort", or "unknown" when the API is missing).

### Proxy (`deploy/Caddyfile`)

- `Cache-Control: no-cache` on `/sw.js`, `/index.html`, `/` and `/manifest.webmanifest`.
- `Cache-Control: public, max-age=31536000, immutable` on `/_expo/static/*`.
- `/@powersync/*` and `/icons/*` keep Caddy's defaults; the service worker serves them from its precache.

## 4. Service worker behaviour

| Request | Handling |
|---|---|
| Navigation to any app path | Precached `index.html`; Expo Router then routes on the client |
| Bundle, worker, WebAssembly, icons, manifest | Precache. A new build downloads only files whose content hash changed |
| `/auth`, `/api`, `/sync`, `/email-templates`, `/local-ca.crt` | Not handled by the worker; straight to the network |

- On first install the worker claims the page, so the app works offline after the first visit without a second reload.
- **Update flow:** the browser fetches `sw.js` (never cached by HTTP, per §3) on each launch and on each `update()` call. A changed `sw.js` installs in the background and waits. The banner appears; tapping it activates the new worker, the page reloads on `controllerchange`, and old precaches are deleted.
- **Failures:** if registration fails (a non-secure origin such as `http://192.168.x.x:8090`, a refusal by Safari, or too little space for the precache), the app behaves as it does today and logs the error to the console.

## 5. Session and local data

### The problem today

`SessionProvider` calls `auth.getSession()` at start-up. If the access token has expired (one-hour lifetime) and renewing it fails because the network is unreachable, auth-js 2.117 returns `{ session: null, error }`. The provider reports `signedOut`, and `DatabaseSessionBridge` calls `disconnectAndClear()`, deleting local recipes and the upload queue. With an offline-capable app shell this becomes the normal path for opening the app on a plane.

### Two separate decisions

`apps/mobile/src/session/sessionState.ts` holds two pure functions with unit tests.

1. **`resolveSession(result, stored)`** decides the session state from the `getSession()` result and the session saved in storage:
   - A session returned means `signedIn`.
   - No session with a retryable network error (`isAuthRetryableFetchError`), and a valid saved session, means `signedIn` with `stale: true`. `userId` and claims come from the saved session's user and access token. The claims are used only by the UI and the local database; the server checks a fresh token on every request.
   - Anything else means `signedOut`.

   auth-js keeps the saved session in storage after a retryable failure, and its auto-refresh retries about every 30 seconds while the app is visible. A successful refresh emits `TOKEN_REFRESHED`, the state loses `stale`, and the bridge connects. A `SIGNED_OUT` event (the server rejected the refresh token) means `signedOut`.

2. **`localDataAction(event, owner, nextUserId)`** decides what happens to the local database:
   - `signOut` (the user tapped Sign out) means `wipe`.
   - `signedIn` with a recorded owner that differs from `nextUserId` means `wipe`, then connect.
   - `signedIn` as the recorded owner, or with no owner recorded, means `keep`, then connect.
   - `signedOut` without the user asking (session ended by the server) means `keep` and disconnect.

   The owner's user ID is stored in `localStorage` under `recipes.dbOwner`, set after a connect and cleared after a wipe. It is an ID, not a secret.

`SessionProvider` reads the saved session through the auth client's storage key and calls `resolveSession`. The `signOut()` action records that the sign-out was the user's own before calling `auth.signOut({ scope: 'local' })`. `DatabaseSessionBridge` calls `localDataAction` and keeps its existing serialised queue and the offline disconnect.

## 6. Storage on Safari

- `database.web.ts` passes `vfs: WASQLiteVFS.OPFSCoopSyncVFS` to `WASQLiteOpenFactory`, with the dedicated-worker setup that mode requires (`vfsRequiresDedicatedWorkers`). The plan's first task confirms this works with the worker files `copy-assets` already provides, before anything else depends on it.
- If the database fails to open, the app shows "This browser can't store recipes on this device. Private browsing isn't supported." instead of a blank screen.
- At start-up the app calls `navigator.storage.persist()` once and shows the result in the footer (§3). Home-screen apps on iOS are also exempt from Safari's seven-day clearing of website data.

## 7. Testing

### Unit (Vitest)

- `resolveSession`: valid session; expired token with a network error and a saved session; a network error with no saved session; a server rejection.
- `localDataAction`: user sign-out; same user returning; different user; no owner recorded; involuntary sign-out.

### End to end (Playwright, Chromium, against the built app in the proxy)

1. **Offline cold start:** sign in, add a recipe, wait for `navigator.serviceWorker.ready` and a controller. Go offline and reload: the list renders with the recipe and the status reads "Offline". Add a recipe, go online, and it reaches a second member's session.
2. **Expired token offline:** set the saved session's `expires_at` in the past, go offline, reload. Still signed in, with the data. Back online, the token renews and sync resumes.
3. **Session ended by the server:** call GoTrue's `/logout` with `scope=global` for the user while they have an unsynced recipe. The app reaches the sign-in screen and the local data remains. Signing back in as the same user uploads the recipe; signing in as a different user shows none of the old data.
4. **Installability:** `/manifest.webmanifest` has the fields in §3 and every icon URL returns an image; `sw.js` and `/` are served with `no-cache`; a file under `/_expo/static/` is served with `immutable`.

The existing 13 specs must pass with the service worker active and the new storage mode.

### Not automated

The update banner, which needs two different builds. It is covered by the owner's checklist.

### Owner's checklist on the iPhone

1. Open `https://<LAN_HTTPS_HOST>:8443` in Safari, Share → Add to Home Screen; the icon and name "Recipes" appear.
2. Open from the home screen: full screen, no address bar. Sign in.
3. Airplane mode on, close the app fully, reopen: recipes show, status "Offline". Add one; it shows as unsynced. Airplane mode off: it syncs and appears on the PC.
4. Rebuild on the PC (`pnpm dev:backend`). Bring the app to the front: the banner appears; tap Reload; the build label changes.
5. Restart the phone and reopen: still signed in, data present.
6. Leave it for a few days and reopen: still signed in, data present, footer shows the storage status.
