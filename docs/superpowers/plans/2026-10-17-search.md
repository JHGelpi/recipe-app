# Search Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Type a word on the Recipes list and see every recipe with it in the title, ingredients or tags, narrowed by tag chips, offline and in under 300 ms over 2,000 recipes.

**Architecture:** Pure search functions in `packages/domain` build an in-memory index from the recipes the list already loads and match every typed word as a substring, ranked by field. The list hook reads rows with a light parser, rebuilds the index only when data changes, and the screen renders results in a virtualized `FlatList`.

**Tech Stack:** TypeScript, Expo 57 (React Native Web), `@powersync/react` live queries, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-17-search-design.md`

## Global Constraints

- Shell commands are prefixed with `rtk`. pnpm via corepack; on the owner's WSL machine a `pnpm` shim must be on `PATH`. Commit messages go in a file and use `rtk proxy git commit -q -F <file>`, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`, referencing FR-19, FR-20, NFR-6.
- Fields searched: title, ingredient lines as typed (`raw`), tags. Not steps, not notes.
- Normalisation: NFD with combining marks removed, lowercase, whitespace runs collapsed, trimmed.
- Every word must be a substring of one field; every selected tag must be in the recipe's tags exactly.
- Score per word: best field (title 3, tag 2, ingredient 1), +1 when the occurrence starts a word. Order: score descending, then title lowercased, then id. With no words: title lowercased, then id.
- Copy: search box label and placeholder "Search recipes"; clear button label "Clear search text"; tag chip label "Tag <tag>"; result line "1 recipe" / "N recipes" (only while searching or filtering); empty result "No recipes match" with a "Clear search" button.
- Speed budget in unit tests (Node): build 2,000 entries < 1,000 ms; three-word search < 100 ms.
- No new dependency. No change to the server, the database, or sync.

## Review Focus

1. **Characters that mean something in a pattern** (`(`, `+`, `*`, `.`, `?`): "1 (14" or "c++" must search as plain text and never throw. Test in Task 1.
2. **A very long or whitespace-only query:** a pasted paragraph returns no matches without slowing typing; spaces alone mean "no words" and list everything. Test in Task 1.
3. **A recipe arriving by sync while a search is active:** it appears in the results when it matches, without retyping. Test in Task 3 (the updated sync specs search on the receiving device before the recipe arrives).
4. **A selected tag that does not exist in the other tab:** switching to Favorites with "dinner" selected shows "No recipes match" with Clear search, not a blank list. Test in Task 3.
5. **Absence checks in a virtualized list are vacuous unless searched:** "the other household never sees it" must search for the title before asserting zero. Covered by Task 3's rule for updating existing specs.

`packages/domain/src/search.ts`:

```ts
/** What search needs from a recipe. */
export type SearchSource = { id: string; title: string; ingredients: string[]; tags: string[] };

export type SearchEntry = {
  id: string;
  sortKey: string;
  text: { title: string; ingredients: string; tags: string };
  tags: string[];
};

type Field = keyof SearchEntry['text'];
const WEIGHT: Record<Field, number> = { title: 3, tags: 2, ingredients: 1 };
const FIELDS: Field[] = ['title', 'tags', 'ingredients'];

/** Lowercase, accents removed, whitespace collapsed: applied to recipes and queries alike. */
export function normalizeSearchText(text: string): string {
  return text
    .normalize('NFD')
    .replace(/\p{M}+/gu, '')
    .toLowerCase()
    .replace(/\s+/g, ' ')
    .trim();
}

/**
 * One entry per recipe. Ingredient lines and tags are joined with a newline,
 * so a word never matches across two of them. Rebuilt only when recipes change.
 */
export function buildSearchIndex(recipes: SearchSource[]): SearchEntry[] {
  return recipes.map((recipe) => ({
    id: recipe.id,
    sortKey: recipe.title.toLowerCase(),
    text: {
      title: normalizeSearchText(recipe.title),
      ingredients: recipe.ingredients.map(normalizeSearchText).join('\n'),
      tags: recipe.tags.map(normalizeSearchText).join('\n'),
    },
    tags: recipe.tags,
  }));
}

function wordsOf(query: string): string[] {
  return [...new Set(normalizeSearchText(query).split(' ').filter((word) => word !== ''))];
}

const BOUNDARY = /[\s\p{P}]/u;

function startsWord(text: string, at: number): boolean {
  return at === 0 || BOUNDARY.test(text[at - 1] ?? '');
}

/** The best score this word earns in any field; 0 when it is in none. */
function wordScore(entry: SearchEntry, word: string): number {
  let best = 0;
  for (const field of FIELDS) {
    const text = entry.text[field];
    let at = text.indexOf(word);
    if (at < 0) continue;
    let atStart = false;
    while (at >= 0 && !atStart) {
      atStart = startsWord(text, at);
      at = text.indexOf(word, at + 1);
    }
    best = Math.max(best, WEIGHT[field] + (atStart ? 1 : 0));
  }
  return best;
}

const compare = (a: string, b: string) => (a < b ? -1 : a > b ? 1 : 0);

/**
 * Ids of the recipes matching every word (as plain-text substrings) and every
 * selected tag (exactly), best first. No words: everything, alphabetically.
 */
export function searchRecipes(
  index: SearchEntry[],
  query: string,
  selectedTags: string[],
): string[] {
  const words = wordsOf(query);
  const matches: { entry: SearchEntry; score: number }[] = [];
  for (const entry of index) {
    if (!selectedTags.every((tag) => entry.tags.includes(tag))) continue;
    let score = 0;
    let matched = true;
    for (const word of words) {
      const points = wordScore(entry, word);
      if (points === 0) {
        matched = false;
        break;
      }
      score += points;
    }
    if (matched) matches.push({ entry, score });
  }
  matches.sort(
    (a, b) =>
      b.score - a.score || compare(a.entry.sortKey, b.entry.sortKey) || compare(a.entry.id, b.entry.id),
  );
  return matches.map((match) => match.entry.id);
}
```

```ts
export type ListRow = SearchSource & { starred: boolean };

function listOf(value: unknown): unknown[] {
  try {
    const list = jsonList(value);
    return Array.isArray(list) ? list : [];
  } catch {
    return [];
  }
}

/**
 * A list row for display and search. Lighter than rowToRecipe (no schema
 * check per row): it keeps what it can read and drops the rest, so an odd row
 * still lists by its title.
 */
export function listRowFrom(row: Record<string, unknown>): ListRow {
  return {
    id: String(row.id),
    title: typeof row.title === 'string' ? row.title : '',
    tags: listOf(row.tags).filter((tag): tag is string => typeof tag === 'string'),
    ingredients: listOf(row.ingredients).flatMap((item) => {
      const raw = (item as { raw?: unknown } | null)?.raw;
      return typeof raw === 'string' ? [raw] : [];
    }),
    starred: Boolean(row.starred),
  };
}
```

```ts
/**
 * The current tab's recipes matching the search, best first, live from the
 * local database. The index is rebuilt only when the rows change, never per
 * keystroke.
 */
export function useRecipeSearch(
  userId: string,
  favoritesOnly: boolean,
  query: string,
  selectedTags: string[],
): { items: ListItem[]; total: number; tags: string[] } {
  const { data } = useQuery<Record<string, unknown>>(
    favoritesOnly ? LIST_FAVORITES_SQL : LIST_RECIPES_SQL,
    [userId],
  );
  const rows = useMemo(() => data.map(listRowFrom), [data]);
  const index = useMemo(() => buildSearchIndex(rows), [rows]);
  const byId = useMemo(() => new Map(rows.map((row) => [row.id, row])), [rows]);
  const tags = useMemo(() => [...new Set(rows.flatMap((row) => row.tags))].sort(), [rows]);
  const items = useMemo(
    () =>
      searchRecipes(index, query, selectedTags).flatMap((id) => {
        const row = byId.get(id);
        return row ? [{ id: row.id, title: row.title, tags: row.tags, starred: row.starred }] : [];
      }),
    [index, byId, query, selectedTags],
  );
  return { items, total: rows.length, tags };
}
```

```markdown
# 0011. Search with an in-memory index over the local database

- **Status:** Accepted
- **Date:** 2026-10-17
- **Builds on:** ADR-0004 (offline-first), ADR-0010 (recipe content as JSON)

## Context
Users type a word and expect every recipe mentioning it in the title, ingredients or tags (FR-19), offline (FR-20), in under 300 ms over 2,000 recipes on a mid-range phone (NFR-6). ARCHITECTURE.md had assumed SQLite FTS5.

## Decision
The recipe list already loads the household's recipes from the local database. `packages/domain` builds an in-memory index from them (title, ingredient lines, tags, normalised for case, accents and whitespace) only when the data changes. Each keystroke matches every word as a plain substring and every selected tag exactly, ranked by field (title, then tag, then ingredient, with a bonus at the start of a word). The list renders results in a virtualized `FlatList`.

## Alternatives considered
- **SQLite FTS5 with the trigram tokenizer:** scales furthest and all PowerSync SQLite builds include it, but it needs triggers on PowerSync's internal `ps_data__recipes` table, matches only 3 or more characters, and is testable only end to end.
- **SQL `LIKE` over JSON at query time:** no index, but scans every recipe's JSON on every keystroke.

## Consequences
- Search is pure, unit-tested functions; partial words of any length work.
- Rebuilding the index after a change parses every listed recipe (tens of milliseconds at 2,000).
- Memory holds one search string per recipe.
- If collections outgrow memory, FTS5 with trigram can replace the index behind the same `searchRecipes` interface.
- Steps and notes are not searched, and there is no typo tolerance.
```
